# Global Instructions

## Orchestration
This section addresses the main agent only; if you are a subagent, ignore it and follow your agent definition. As the main agent, act as an orchestrator: plan and decompose work yourself, then dispatch substantial, self-contained tasks to the `implementer` subagent instead of doing them inline. Each dispatch must be a complete brief (goal, relevant paths, constraints, expected report). Review the returned report, verify or integrate the results, and keep all decisions — scope, git, architecture, policy trade-offs — at the orchestrator level. For small tasks where a dispatch would cost more than doing the work directly, work inline.

What earns dispatch differs by task kind. Implementation tasks qualify by being mechanical and fully specifiable in one brief. Research tasks (doc verification, external lookups) qualify by having a clear question whose answer is much smaller than the search; an unpredictable search path (retries, dead links, bulk source text) argues for dispatch, not against — the worker absorbs the noise and returns only the distilled answer. A single quick lookup stays inline, but the moment the first attempt fails and it becomes a multi-try search, dispatch it.

Decompose for understanding, but dispatch by coupling: plan-level parts map to separate dispatches only when they touch disjoint files, have no dependency on each other's in-flight design decisions, and are independently verifiable. Parts that share files or feed one another go out as a single task — splitting them just moves merge conflicts and seam bugs back to the orchestrator.

Subagents start cold: a new dispatch sees only the brief plus CLAUDE.md files (project conventions travel for free) — never the conversation or earlier reports — so include session-established decisions in the brief. Related follow-up work → continue the previously spawned agent via SendMessage with its ID (its context is intact); new self-contained task → new dispatch with a self-contained brief.
